# Architecture

This repo contains two things layered on top of each other: the **appcraft CLI/template engine**, and the **generated-project framework** that the CLI's `base` template installs into user projects. Keep straight which one you're editing.

## 1. CLI / template engine (`appcraft/cli.py`, `appcraft/scripts/`, `appcraft/utils/template/`, `appcraft/templates/template_abc.py`, `appcraft/templates/template_manager.py`)

- `cli.py` is a thin dispatcher: `sys.argv[1]` selects a command (`init`, `add_template`, `list_templates`, `save_template`) from a dict mapping to functions in `appcraft/scripts/`.
- **`TemplateABC`** (`templates/template_abc.py`) is the base class every template subclasses. Its metaclass auto-derives `name` from the defining module's filename, requires a `description` string, and freezes `default`/`description` as read-only class attributes. Class attributes templates can set:
  - `active` (default `False`) — whether the template is finished/ready. Inactive templates are hidden from `list_templates` and rejected by `init`/`add_template` unless `--install-inactive` is passed. Use this for templates still under development (see [templates-misc.md](templates-misc.md) for the current inactive ones).
  - `standalone` (default `True`) — set to `False` when a template only makes sense as another template's dependency and must never be installed by name directly. See `templates/flask/__init__.py` (depended on by `flask_api`/`flask_ui`) and `templates/web_scraping/__init__.py` (depended on by `selenium`/`playwright`/`httpx`/`curl_cffi`) — details in [templates-flask.md](templates-flask.md) and [templates-web-scraping.md](templates-web-scraping.md).
  - `default` (default `False`) — auto-included in every `init` regardless of what was requested (`base`, `poetry`).
  - `dependencies` — list of other template names installed first (transitively resolved by `TemplateLoader.resolve()`).
  - `exclusive_group` (default `None`) — templates sharing a non-`None` group string can't be requested *together* in the same `init`/`add_template` call (`TemplateLoader.resolve()` raises `TemplateConflictError`). Requesting just one when a *different* member of the group is already installed is a deliberate swap, not a conflict: `TemplateABC.install()` itself detects this (any other installed template sharing `cls.exclusive_group`, via `TemplateManager`) and calls that other template's `.uninstall()` first, automatically — generic engine behavior, not something each template has to implement. The only current user is `package_manager` (`poetry`/`pipenv`/`uv` — see [templates-package-managers.md](templates-package-managers.md)), but this isn't package-manager-specific.
  - `pre_install(cls, target_dir)` — optional hook run **before** dependencies are installed (see install-order note below). Used when a template needs to change the project *before* `PackageManagerBase()` picks a package manager and installs requirements — e.g. `pipenv`/`uv` rewriting which package manager owns `config/app.toml`'s `manager`.
  - `post_install(cls, target_dir)` — optional hook run **after** the environment is fully installed. Used for one-time side effects that need a working project, e.g. `templates/git/__init__.py` running the generated app's own entrypoint to `git init`.
  - `TemplateABC.is_installed()` checks whether `cls.name` is a key in `TemplateManager().load_templates()` — this also works *inside a generated project at runtime* (not just from the CLI), see the `project_init` bullet below for how that's wired up.
- **Install order**: `project_init`/`add_template` call, for every resolved template, in this exact sequence: (1) copy the template's `templates/<name>/files/` tree, (2) call `pre_install()` for every template that defines one, (3) install the package manager's requirements, (4) call `post_install()` for every template that defines one. Prefer `is_installed()` (re-checked on every run) over a `pre_install`/`post_install` source-rewrite (a one-shot action) for "does another optional template change my behavior" logic — e.g. `application/providers/adapters/database.py` picking `SQLAlchemyAdapter`/`MongoDBAdapter` over the default `MemoryAdapter` when installed (see [templates-database.md](templates-database.md)), or `flask`'s `app.py` conditionally registering API/UI blueprints (see [templates-flask.md](templates-flask.md)). This is the framework's single most-reused pattern — every "family" doc below has its own concrete instance of it.
- `install()`/`uninstall()` are the imperative counterparts to the hooks above. `install(target_dir=None)` first runs the `exclusive_group` auto-swap check described above, then copies the template's files (via `TemplateAdder`) and merges its `pyproject.toml`/`Pipfile` dependencies (via `merge_pm_files`) — both `project_init` and `add_template` call it, so a template's dependencies and hooks run the same way whether it's installed at project creation or added later. `uninstall(target_dir=None)` deletes whichever files `TemplateManager` recorded as this template's own (skipping any also owned by another still-installed template, e.g. a shared base's files) and removes its `templates.json` entry via `TemplateManager.remove_template()` — so `is_installed()` correctly flips right after a swap. It's a generic, file-tracking-based default; a template doesn't need to override it unless it has untracked side effects to also undo (e.g. a `pre_install` that wrote a file directly, like `pipenv`'s `Pipfile` — that specific case is already handled by the *next* installed template's own `pre_install` calling `clear_dependency_sources()`, not by `uninstall()` itself, see [templates-package-managers.md](templates-package-managers.md)).
- **`TemplateLoader`** (`utils/template/loader.py`) walks `appcraft/templates/*/`, imports each package, and collects `TemplateABC` subclasses (filtering on `active`/`default`). Its `resolve(template_names, requested_template_names=None, allow_inactive=False)` validates a requested set of names (existence, `active`, `standalone`, `exclusive_group` — the `active`/`standalone`/`exclusive_group` checks apply only to `requested_template_names`, defaulting to all of `template_names`) and returns them plus their transitive `dependencies` in install order, raising `TemplateNotFoundError`/`TemplateInactiveError`/`TemplateNotStandaloneError`/`TemplateConflictError` otherwise; both `project_init.py` and `add_template.py` call this instead of duplicating the resolution logic.
- **`TemplateAdder`** (`utils/template/adder.py`) copies a template's `templates/<name>/files/` tree into the target project, merges `pyproject.toml`/`Pipfile` dependencies (deep dict/list union via `toml`), and records every copied file path into the target project's `infrastructure/framework/appcraft/templates/templates.json` via `TemplateManager`.
- **`TemplateManager`** (`templates/template_manager.py`) is the on-disk registry (`templates.json` in the *target* project) of which templates are installed and which files each one owns — this is what lets `TemplateSaver` know what to diff later, and what `TemplateABC.uninstall()` deletes. `add_template(template_data)` records a newly-installed template's owned files (no-op with a warning if already present); `remove_template(name)` pops its entry and returns the file list it owned, for the caller to delete. It's copied verbatim into every generated project (see the `project_init` bullet below), so keep it dependency-free apart from stdlib and the generated project's own `infrastructure/framework/appcraft/...` modules — never import from the `appcraft` CLI package here, that only exists in the dev environment.
- **`TemplateSaver`** (`utils/template/saver.py`, driven by `appcraft save_template <name>`) is the reverse flow: it syncs edits made in the `templates/temp/files` scratch project back into a real template's `files/` directory, adding new/changed files and pruning ones that were deleted. See the workflow below.
- **`TemplateCreator`** (`utils/template/creator.py`) scaffolds a brand-new template directory from the `base` template (not currently wired into `cli.py`'s command dispatch — invoke it directly if adding a new template). `scripts/create_runner.py` is a lighter, dev-only helper in the same boat (not in `cli.py`'s `COMMANDS`): it scaffolds a single standalone `Runner` subclass into an *existing* project's `runners/main/` or `runners/tools/` (`--target`), for when you just want one more runner rather than a whole new template.
- `project_init` (`scripts/project_init.py`) and `add_template` (`scripts/add_template.py`) both call `TemplateLoader.resolve()` then `template.install()` (plus `pre_install()`/`post_install()`) for each resolved template — `project_init` additionally always includes `default_template_names` (`base`/`poetry`) and, when run from the repo root or `temp/files`, wipes and `chdir`s into `temp/files` first (see the workflow below); `add_template` operates on the current directory as-is, for adding templates to a project that already exists. `project_init` also does something not obvious from reading a single template in isolation: **for every template `appcraft` knows about** (not just the ones being installed), it copies that template's own `<name>/__init__.py` (the actual `TemplateABC` subclass file, e.g. `templates/sqlalchemy/__init__.py`) into the generated project at `infrastructure/framework/appcraft/templates/<name>/__init__.py`, alongside fresh copies of `templates/template_abc.py` and `templates/template_manager.py`. This is what makes `SomeTemplate.is_installed()` (and `pre_install`/`post_install`-style logic) callable *from inside the generated project itself* at runtime — without the `appcraft` CLI package being installed there — because `TemplateManager` only needs the target project's own `infrastructure/framework/appcraft/templates/templates.json`, not anything from the `appcraft` package. `Initializer.execute_runner()` and `ComponentPrinter` already rely on this (`importlib.import_module("infrastructure.framework.appcraft.templates.locales")` then `LocalesTemplate.is_installed()`) to conditionally enable the `locales`/`logs` templates' behavior at runtime. (`add_template` doesn't redo this marker copy, so a template created *after* a project's last `init` won't have a marker there until the project is regenerated.)

## Template development workflow (`appcraft/templates/temp/`)

`appcraft/templates/temp/` is not a real, installable template — it is a disposable **example project** used as the sandbox for authoring and editing every other template. There is no other supported way to develop a template than through this loop:

1. From the appcraft repo root (or from inside `appcraft/templates/temp/files` itself), run `python -m appcraft.cli init <template_names...>`. `project_init` detects it's being run from the repo root and, instead of scaffolding into the current directory, wipes `appcraft/templates/temp/files` clean, recreates it, `chdir`s into it, and installs the requested templates there — so `temp/files` becomes a real, runnable generated project containing exactly those templates.
2. Edit/add/remove files inside `appcraft/templates/temp/files` as if it were an ordinary generated project (you can run its runners, add dependencies, etc.) to develop or fix a template's behavior.
3. Run `python -m appcraft.cli save_template <template_name>` from the repo root. `TemplateSaver` reads `temp/files`'s own `infrastructure/framework/appcraft/templates/templates.json` to know which files belong to `<template_name>` versus other templates also installed in `temp`, then copies every new/changed file for `<template_name>` back into `appcraft/templates/<template_name>/files/`, and deletes files/folders there that no longer exist in `temp/files`.
4. Repeat step 1 to reset `temp/files` before starting on the next template — its contents are always throwaway and get wiped on the next `init` run from the repo root.

Because of this wipe-on-`init` behavior, never treat `appcraft/templates/temp/` as a place to keep work — only `appcraft/templates/<name>/files/` (updated via `save_template`) is persisted.

## 2. Generated-project framework (`appcraft/templates/base/files/`)

This is the actual code that ends up in a project after `appcraft init`. It defines the Clean Architecture skeleton and layers:

- `domain/` — models, value objects, filters, and the abstract `types/` (model/port/repository/schema) contracts; no framework or infra dependencies.
- `application/` — use cases, DTOs/schemas, mappers, providers, and repository interfaces; depends only on `domain/`.
- `infrastructure/` — concrete adapters (e.g. `memory/` storage) and `infrastructure/framework/appcraft/` — the runtime that powers every generated project.
- `presentation/` — CLI/web-facing input validation and exception translation.
- `runners/main/` and `runners/tools/` — entry points a project exposes; other templates (`flask`, `sqlalchemy`, `docker`, `github`, `web_scraping`, ...) contribute their own runner files here.

### Naming and layering conventions

These are not enforced by tooling — they're conventions established by `base`, `sqlalchemy`, `mongodb`, `flask`, and `web_scraping` (in that rough chronological order). **`git`/`github` still predate this and use the older `application/services/` + `AdapterInterface` pattern — that's exactly why they're `active = False` rather than left active as a misleading reference, see [templates-git.md](templates-git.md).** When adding or refactoring a template, match the newer convention:

- **`Interface` suffix, no `I` prefix** — a `domain/`-layer contract with zero framework/infra dependencies (e.g. `FilterInterface` in `domain/filters/interface/__init__.py`, `HTMLElementInterface` in `domain/html_elements/interface/__init__.py`). Lives in a `<concept>/interface/` subfolder under the concept's own domain folder, not in a shared `domain/interfaces/` grab-bag.
- **`Port` suffix** — an `application/`-layer abstract contract for something the application depends on but doesn't implement (a database, a browser engine, etc). Subclasses the shared `Port` ABC from `application/ports/__init__.py` and lives at `application/ports/<concept>.py` (e.g. `DatabasePort` in `application/ports/database.py`, `WebScrapingPort`/`WebScrapingAsyncPort` in `application/ports/web_scraping.py`). This is the layer where "interchangeable sibling adapters" (see below) plug in — never `AdapterInterface`, and never under `application/services/`.
- **`Adapter` suffix** — an `infrastructure/`-layer concrete implementation of a `Port` (e.g. `MemoryAdapter(DatabasePort)`, `SQLAlchemyAdapter`, `SeleniumAdapter`). Lives at `infrastructure/<concept>/<engine>/adapter.py` when there are multiple interchangeable engines for one concept (`infrastructure/database/sqlalchemy/`, `infrastructure/web_scraping/selenium/`), or `infrastructure/<concept>/adapter.py` when there's only one.
- **`Repository` suffix** — an `application/`-layer class that orchestrates a `Port` for one specific domain model (e.g. `UserRepository(RepositoryBase[User, NewUser])` in `application/repositories/user.py`), built on the generic `Repository`/`RepositoryBase`/`GenericRepository` in `application/repositories/__init__.py`.
- **`UseCase` suffix** — an `application/`-layer class subclassing `UseCase[TInput, TOutput]` (`application/use_cases/__init__.py`), with a single `.execute()` method. Lives at `application/use_cases/<concept>/<name>.py`. This replaced an older `application/services/` layer — new code should never add to `application/services/`.
- **`<Domain>CLIPresentation` convention** — a `presentation/cli/<concept>.py` (or `<concept>/` folder, one file per use case, if there are several) class taking the relevant use case(s) in `__init__`, with a nested `class Printer(ComponentPrinter)` (`domain = "..."`, `@classmethod` print methods) and outer method(s) that call `.execute()` then print via `Printer`.
- `application/` is normally only allowed to depend on `domain/`, with one accepted exception: introspection-style use cases that need to inspect concrete `infrastructure/` classes directly (not through a `Port`) because the whole point is listing/benchmarking what's installed — e.g. `ListTablesUseCase` importing `SQLAlchemyAdapter` directly, or the web_scraping benchmark use case importing `RunnerDiscovery`/`WebScrapingRunnerBase` from `infrastructure/` (see [templates-web-scraping.md](templates-web-scraping.md)).

### The "interchangeable sibling adapters via `is_installed()`" pattern

The framework's core extensibility mechanism: define a `Port` once (in `base`, or in a template's own base if it's not part of `base`), then let any number of sibling templates each ship a concrete `Adapter` for it. A shared resolver function picks a default among whichever siblings are actually installed (via `SomeTemplate.is_installed()`, never by assuming a specific one is present), with a `config/*.toml` value to break ties and a fallback (in-memory, or another sibling) when nothing else is installed. Three concrete instances, each documented in its own file:

- [templates-database.md](templates-database.md) — `sqlalchemy`/`mongodb`, the simplest case: pure siblings, no shared base template needed (the `Port` already lives in `base`).
- [templates-flask.md](templates-flask.md) — `flask`/`flask_api`/`flask_ui`, a variant where the "siblings" (`flask_api`, `flask_ui`) aren't mutually exclusive alternatives but composable extensions, each independently toggled via `is_installed()` inside the shared `flask` base's own `app.py`.
- [templates-web-scraping.md](templates-web-scraping.md) — `web_scraping`/`selenium`/`playwright`/`httpx`/`curl_cffi`, combining both of the above (a non-standalone shared base *and* true interchangeable siblings) plus a novel mechanism neither of the other two needs: runtime session handoff between two different installed adapters.

### The runner system

`infrastructure/framework/appcraft/core/runner/` is how a generated app's entry point becomes an interactive menu:

1. `Initializer.main()` checks that a venv/package-manager environment is active (`PackageManagerBase`), then calls `execute_runner()`.
2. `RunnerDiscovery` AST-scans `.py` files under the app folder for classes subclassing `Runner`, and reflects each class for methods marked as app runners.
3. `RunnerSelector` presents an interactive `prompt_toolkit` menu to choose module → class → method.
4. `RunnerExecutor` ties discovery + selection together and invokes the chosen method with args/kwargs parsed from the CLI (`key=value` tokens become kwargs).

`PropertyMeta` (`infrastructure/framework/appcraft/core/property_meta.py`) reads a subclass's `__orig_bases__`'s `__args__` to auto-populate a `_adapter_cls`-style attribute from a generic subscript like `DocsSearchRunnerBase[SeleniumAdapter]`, letting a concrete per-engine `Runner` subclass be a one-liner (see [templates-web-scraping.md](templates-web-scraping.md) for the fullest use of this).

Other template directories under `appcraft/templates/` follow the same `<name>/__init__.py` (Template class) + `<name>/files/` (files to copy, mirroring the target project's real directory layout) structure — see the per-family docs linked above, or [templates-misc.md](templates-misc.md) for everything not covered by a dedicated file.
