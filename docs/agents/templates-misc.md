# Everything else

Templates that don't belong to a documented family above, grouped by actual readiness (verified against `active`/file counts as of 2026-10-09 — re-check before relying on this if it's been a while, `active` in each `__init__.py` and `find appcraft/templates/<name>/files -type f | wc -l` are both cheap to re-verify). `docker` gets its own paragraph below rather than a family file — it has no sibling templates, but it's substantial enough (dynamic compose generation, prod/dev split) not to lump in with the stubs.

## Active, standalone utility templates

No sibling family, no shared base — each is a self-contained addition.

- **`prompt_toolkit`** — adds the `prompt-toolkit` dependency (under the `cli` [dependency-group](templates-package-managers.md#delivery-surface-dependency-groups-2026-10-08) — a genuine delivery-surface concern: a build that only ever runs with explicit args, e.g. a cron job, doesn't need it) that powers the runner system's interactive module/class/method menu (see [architecture.md](architecture.md#the-runner-system)). The runner system works without it as long as the full path is always passed on the command line; without this template, only that inline-args mode is available.
- **`docker`** — containerizes the app: a single Dockerfile (installs through whichever of poetry/pipenv/uv is active, non-root user, skips dev-only deps in production), and a `docker-compose.yml` generated automatically from every `runners/main` `Runner` exposing a `start` action — one service per deployable entry point, discovered the same way the web_scraping benchmark tool discovers runners (see [templates-web-scraping.md](templates-web-scraping.md)). `python tools docker {build,up,down,generate_compose}` wraps `docker compose` (falling back to the standalone `docker-compose` v1 binary) so none of that needs `cd infrastructure/docker` first. Flask's own runner is environment-aware (`config/app.toml`'s `environment = "production"` switches it from the Werkzeug dev server to gunicorn) specifically so this template's production path means something.

## `active = False`, real content, never finished/activated

These have actual scaffolding (not stubs) but are hidden from `list_templates`/`init` until someone verifies them and flips `active = True`. Don't assume they're production-ready just because files exist.

- **`locales`** / **`logs`** — the `Pipfile`-only dependency gap (`TemplateAdder._copy_directory_contents` only copies a `Pipfile` for Pipenv-based projects, so a default Poetry project never installed these) fixed 2026-10-08: each now ships a `pyproject.toml` fragment instead (the `Pipfile`s themselves were deleted outright the same day — see the note below), declaring the same dependency as a plain `[project.dependencies]` main dependency — translations and logging are used regardless of which delivery surface is active, not something a "CLI build"/"web build" would ever want to exclude (see [templates-package-managers.md](templates-package-managers.md#delivery-surface-dependency-groups-2026-10-08)). `locales` needed `polib` — its `Pipfile` was actually empty before this (not just un-ported; nothing declared it anywhere, despite `message_manager.py` importing it directly). `logs` needed only `structlog`, the one import `logger.py` actually has — `better-exceptions`/`rich`/`logbook`/`flask-logging`/`graypy` were declared in the old `Pipfile` but never imported anywhere in the template, so they were dropped rather than carried over as dead dependencies. Verified end-to-end (`appcraft init <name> --install-inactive`): `locales`'s `polib` and `logs`'s `structlog` both install for real now, and `get_default_logger()` correctly resolves to `StructlogLogger`, writing both console and file output, with no manual `pip install` needed first. Still `active = False` — the dependency bug is gone, but that's not the same as a full behavioral verification of either template (translation switching for `locales`; log rotation beyond a smoke test for `logs`); re-activate after someone does that.
- **`ci_cd`** (10 files) — CI/CD pipeline scaffolding. Its `Pipfile`'s `[packages]` table was correctly empty, not a gap (`runners/main/deploy.py` is a no-op stub, `def run(self): pass`, with no real dependency to declare yet) — the empty `Pipfile` itself was deleted 2026-10-08 along with every other template's, see below. Nothing to add until `deploy.py` is actually implemented.
- **`data_analysis`** (9 files) — the `Pipfile`-only gap fixed 2026-10-08 the same way (a `pyproject.toml` fragment with the same 5 packages as plain `[project.dependencies]` — a business-logic feature, not a delivery surface, see [templates-package-managers.md](templates-package-managers.md#delivery-surface-dependency-groups-2026-10-08) — `jupyter` kept under `dev`, a genuine dev-only notebook tool; the `Pipfile` itself is gone, see below). A second problem turned up verifying it end-to-end: the `Pipfile`'s original exact pins (`pandas==2.2.3`, `numpy==2.1.1`, `matplotlib==3.9.2`, `scikit-learn==1.5.2`, all from 2024) have no prebuilt wheel for Python 3.14 and fail to build from source in this sandbox (`numpy`'s own build chain breaks compiling its `x86-simd-sort` vendor code). Repinned to current, wheel-available versions instead (`pandas==3.0.6`, `numpy==2.5.3`, `matplotlib==3.11.2`, `scikit-learn==1.9.1`; `seaborn==0.13.2` and `jupyter==1.1.1` were already current and stayed). `domain/models/data_analysis.py`'s `DataSet`/`DataSummary`/`CorrelationAnalysis`/`DataCleaning`/`FeatureEngineering` classes still don't import any of them — still a hand-rolled, illustrative sketch over plain `list[dict]` records (`CorrelationAnalysis.calculate_correlation()` literally hardcodes `0.75` for every column). Intended direction (2026-10-07, unchanged): real DataFrame-backed tooling — reading/writing Excel and JSON, cleaning and summarizing data with pandas — replacing these placeholders is separate work from the dependency fix.
- **`data_visualization`** (8 files) — includes a `domain/models/charts.py` and Sphinx docs config, and unlike the others above, no `pyproject.toml` fragment at all yet (and never had a `Pipfile` either). `charts.py`'s `Chart`/`BarChart`/`LineChart`/`PieChart` classes have no charting library wired in either — `plot()` on each one just `print()`s what it would draw. Intended direction (2026-10-07): real chart generation with matplotlib, replacing these placeholders.

**No template ships a `Pipfile` any more (2026-10-08).** Every template that had one (`ci_cd`, `data_analysis`, `flask_ui`, `locales`, `logs`, `machine_learning`, `mongodb`, `prompt_toolkit`, `sqlalchemy`, `tests`, `websockets`) had its content migrated into a `pyproject.toml` fragment instead (one was created from scratch for `machine_learning`/`tests`/`websockets`, which previously had no `pyproject.toml` at all — see below), then the `Pipfile` was deleted. This was safe because the per-template `Pipfile`-merge path had never actually worked: see [templates-package-managers.md](templates-package-managers.md) for why (`TemplateABC.package_manager` always defaulting to `PoetryManager()`, so `TemplateAdder`'s Pipenv-specific branches never fired for any template, ever). Two real, unrelated bugs turned up migrating `sqlalchemy`'s: its `Pipfile` declared `psycopg2-binary`, while its `pyproject.toml` (and the actual adapter code) target `psycopg` (v3) — fixed to `psycopg` — and `flask-sqlalchemy` (imported by `flask/files/infrastructure/framework/flask/sqlalchemy.py`, but only when `sqlalchemy` is also installed) had never been declared in *any* `pyproject.toml`, only in `sqlalchemy`'s now-deleted `Pipfile` — a default Poetry project combining `flask`+`sqlalchemy` silently never installed it (masked by a `try/except` around the code that needed it). Now declared in `sqlalchemy`'s `pyproject.toml`. `mongodb`'s `Pipfile` also carried `mongoengine`/`flask-pymongo`/`motor`/`mongomock`, none of which anything in the template imports — dropped rather than ported, same rationale as `logs`' pruned dependencies above.

Check each one's actual layer usage before treating it as a naming-convention reference — it hasn't been confirmed to follow the [current conventions](architecture.md#naming-and-layering-conventions) the way the active templates have.

## Pure stubs — description only, no scaffold at all

`TemplateABC` subclass exists (so they can be referenced/discussed), but `files/` is empty or near-empty. These are ideas on the roadmap, not started:

- **`graphql`** (0 files)
- **`rabbitmq`** (0 files)
- **`machine_learning`** — still no real scaffold (just `__init__.py`), but now also carries a `files/pyproject.toml` declaring its aspirational dependency list (`scikit-learn`/`tensorflow`/`keras`/`torch`/`xgboost`/`lightgbm`/`matplotlib`/`seaborn`/`statsmodels`/`joblib`/`optuna`/`hyperopt`/`imbalanced-learn`) as plain `[project.dependencies]` — a business-logic feature once real code exists, not a delivery surface — migrated 2026-10-08 from what used to be its only file, a `Pipfile` (now deleted, see above).
- **`websockets`** — same scaffold state, but its dependency list (`websockets`/`python-socketio`/`aiohttp`/`websocket-client`) lives under the `web` [dependency-group](templates-package-managers.md#delivery-surface-dependency-groups-2026-10-08) instead of a plain main dependency: a websocket server is a network-facing delivery surface, same bucket as Flask's HTTP server, not a business feature — even though neither template depends on the other.
- **`tests`** — same scaffold state, just `__init__.py` plus a migrated `files/pyproject.toml` — but under the `dev` group (`pytest`/`mock`/`coverage`/`tox`/`pytest-cov`/`pytest-mock`/`flaky`/`factory-boy`), not its own group: test tooling is a dev-time concern regardless of delivery target, the same reasoning as `data_analysis`'s `jupyter` above. Worth a second look before ever building this one out: the project itself has [no automated test suite](../../AGENTS.md), so a "tests template" that scaffolds testing setup for *generated* projects is a different, narrower scope than it might sound like — confirm intent before starting. (Unrelated pre-existing oddity, not touched: `appcraft/templates/tests/pyproject.toml`, directly under the template root rather than `files/`, is dead `[tool.pytest]` config that no install path ever copies — not the same file as the new `files/pyproject.toml` dependency fragment.)

## Framework-level quality gaps (not a specific template)

- No automated test suite for `appcraft` itself (confirmed in the root `AGENTS.md`) — `TemplateLoader.resolve()`, `install()`/`uninstall()`, `TemplateSaver`, etc. have zero test coverage despite `pyright --strict` being enforced.
- CI (`.github/workflows/docs.yml`) only accumulates a release's already-frozen, already-built docs into the `docs` branch and publishes to GitHub Pages — it doesn't run `sphinx-build` itself, let alone `pyright` or any lint/type-check, on push/PR. All such verification today is manual (`pyright`/`sphinx-build` from the repo root).
