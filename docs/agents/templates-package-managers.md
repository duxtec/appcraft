# Package manager templates (`poetry`, `pipenv`, `uv`)

All three share `exclusive_group = "package_manager"` (see the `TemplateABC` attribute reference in [architecture.md](architecture.md)) — `TemplateLoader.resolve()` rejects requesting two of them *together* in one `init`/`add_template` call (`TemplateConflictError`). Installing one when a different one is already present is a deliberate swap: `TemplateABC.install()` automatically calls the currently-installed sibling's `.uninstall()` first (generic `exclusive_group` behavior, not specific to package managers — see [architecture.md](architecture.md)), and each template's own `pre_install` converts whatever dependency state that leaves behind into its own format. None of the three depends on another — swapping in either direction works the same way.

## Where the manifest actually lives

`base` ships the project's *only* `pyproject.toml` (`base/files/pyproject.toml` — real baseline deps `toml`/`pydantic`/`injector`, dev deps `sphinx`/`flake8`/`black`/`isort`, and project metadata/`[build-system]`), not `poetry`. `poetry`/`pipenv`/`uv` never ship a full manifest of their own — each only ships a small fragment declaring `appcraft` as a dev dependency (for `pre_install`'s own import, see below) merged in via `TemplateAdder.merge_toml`. This is why none of the three needs to depend on another to guarantee something exists to read from: `base` is unconditionally installed before any package-manager template's `pre_install` runs (its own `install()` file-copy happens in an earlier phase — see the install-order note in [architecture.md](architecture.md)).

**No template ships a static `Pipfile` of its own — ever** (fixed 2026-10-08, see `docs/agents/templates-misc.md` for the per-template history). Every template that declares a dependency does so in exactly one place, its own `files/pyproject.toml` fragment; a Pipenv-managed project's actual `Pipfile` only ever exists as `pipenv`'s own *generated* output (its `pre_install` writing `read_dependencies()`'s snapshot straight to `Pipfile`, see below) — never as a file copied from any template's `files/` tree. This was already true in effect before the cleanup, just accidentally: `TemplateAdder.merge_pm_files` picked `"Pipfile"` as the merge target only when `self.package_manager` was a `PipenvManager`, but `TemplateABC.package_manager` defaults to `PoetryManager()` and no template ever overrode it (not even `pipenv`/`uv` themselves, whose own `install()` call uses the same default) — so that branch, and the matching `Pipfile`-skip condition in `_copy_directory_contents`, had never actually fired for any template, ever (confirmed empirically: `add_template mongodb` against an already-Pipenv-converted project left its `Pipfile` completely unchanged). `merge_pm_files` was removed outright (`TemplateABC.install()` now calls `TemplateAdder.merge_toml(cls.name)` directly, which always targets `pyproject.toml`) along with the dead `Pipfile`/`Pipfile.lock` branch in `_copy_directory_contents` — nothing is lost, since neither one had any effect to begin with.

**Every file inside a template's `files/` directory is written in plain Python packaging form, never a package-manager dialect** (fixed 2026-10-08 — `base/files/pyproject.toml` and every other template's own `pyproject.toml` fragment, e.g. `flask/files/pyproject.toml`, used to be hand-written as `[tool.poetry.dependencies]`/`[tool.poetry.group.dev.dependencies]` tables with Poetry's caret/tilde ranges, baking in an assumption that Poetry is always the active manager). They're pure PEP 621/735 now: `[project]` with a `dependencies = [...]` list of PEP 508 requirement strings, `[dependency-groups]` for dev-only groups (`dev = [...]`), PEP 639 string licenses (`license = "MIT"`). A fragment like `flask/files/pyproject.toml` is intentionally not a standalone-valid `pyproject.toml` on its own (no `name`, since it's never built/read except as a merge source) — this mirrors how it was already incomplete on its own before this change, just in the other dialect. `TemplateAdder.merge_toml`'s `union_dicts` deep-merges every installed template's `[project].dependencies`/`[dependency-groups].*` list straight onto `base`'s own (list-extend with dedup), so by the time any package-manager template's `pre_install` runs, the whole project's merged dependency set is sitting in one pure-PEP-621 `pyproject.toml` — regardless of which package manager ends up converting it. This is what satisfies "a package-manager-specific format only applies once that manager's template is actually installed": nothing manager-specific is baked into any template's shipped files, only into what `poetry`/`pipenv`/`uv`'s own `pre_install` writes at install time.

## Delivery-surface dependency-groups (2026-10-08)

Beyond `dev`, a dependency lives under a named PEP 735 group instead of `[project.dependencies]` **only when it's specific to how the app is *delivered/exposed*, not to a business feature it uses**: `flask`/`flask_ui` (and `sqlalchemy`'s own `flask-sqlalchemy`, only needed when Flask is also present), plus the unrelated `websockets` stub's own packages (a websocket server is another network-facing delivery surface, same bucket, even though neither template depends on the other) → `web`; `prompt_toolkit` → `cli`; a future desktop/mobile template → `gui` (nothing ships there yet). Think "what would a CLI-only build, a web-server build, and a desktop-GUI build each *not* need from one another" — that's the only axis these groups model.

Everything else — `sqlalchemy`/`mongodb` (`database`), `selenium`/`playwright`/`httpx`/`curl_cffi` (`web_scraping`), `locales` (`i18n`), `logs` (`observability`), `data_analysis` (`data`), `machine_learning`'s stub list — stays a plain `[project.dependencies]` main dependency, same as `base`'s own `toml`/`pydantic`/`injector`. These are business-logic concerns: a use case that reads from the database, scrapes a page, or translates a string needs that dependency *regardless* of whether the app is being driven by a CLI, served over HTTP, or wrapped in a desktop GUI — there is no delivery target where excluding them wouldn't just break the app. (A first pass at this got this distinction backwards — `database`/`web_scraping`/`i18n`/`observability`/`data` were briefly their own excludable groups too, reverted the same day once this was pointed out, together with folding `tests`' pytest/coverage/etc into `dev`, since test tooling is a dev-time concern regardless of delivery target, not a delivery surface or a business feature.)

This only works because **every group installs by default, and is only ever opt-out, never opt-in** — the same semantics `dev` already had. A template you installed isn't optional at runtime (the code is there and imports it unconditionally), so a group a package manager doesn't install by default would silently break the generated project. Concretely, per manager:

- **Poetry**: a group without `optional = true` installs by default and is excluded with `poetry install --without <group>` — this is already true for *any* number of groups, named however, with zero changes to `poetry`'s `pre_install` (it already builds `[tool.poetry.group.<name>.dependencies]` generically from every `snapshot.groups` entry, never just `"dev"`). Poetry also reads a plain, `[tool.poetry]`-free `[dependency-groups]` table the same way (confirmed empirically) — relevant to [AGENTS.md](../../AGENTS.md)'s own root `pyproject.toml`, which has no `[tool.poetry]` table at all.
- **uv**: only its own `dev` group installs by default on a bare `uv sync` — any other named group needs either `--group <name>` every time, or `[tool.uv].default-groups` listing it. `uv`'s `pre_install` now sets `default-groups` to *every* group name present (`dev` included — confirmed empirically that setting `default-groups` at all *replaces* uv's implicit default rather than adding to it, so leaving `"dev"` out of an explicit list would silently stop installing it). `uv sync --no-group <name>` excludes one.
- **Pipenv**: structurally can't do this at all. A bare `pipenv install` only ever installs `[packages]` — `[dev-packages]` and any custom category need an explicit `--dev`/`--categories` flag (confirmed empirically), there is no "default-included but excludable" named-group concept in the Pipfile format. So `pipenv`'s `pre_install` flattens *every* group — `dev` included — into `[packages]`, to at least keep a bare `pipenv install`'s default behavior matching Poetry/uv's (everything installed). The real cost: Pipenv can't exclude a single group for a lean/production install the way `poetry install --without`/`uv sync --no-group` can, and converting *away* from Pipenv to Poetry/uv afterwards permanently loses the original group boundaries (everything reads back as one flat `main` group, since Pipfile's `[packages]` doesn't remember where each entry came from) — an inherent, accepted limitation of the format, not a bug to chase further.

## `uv` (active)

All three (including `poetry`) switch dependency management to their own format by reading whatever currently exists and rewriting it — fully symmetric, so swapping in any direction (poetry → pipenv → uv → poetry → ...) round-trips the same dependencies, groups, and metadata each time:

- `pre_install(cls, target_dir)` calls `appcraft.utils.dependency_convert.read_dependencies(target_dir)` to snapshot current dependencies (main + every named group, not just dev + Python version + project metadata) regardless of source format (Poetry-, uv-, or Pipfile-style — whichever is currently in `pyproject.toml`/`Pipfile`), then writes that snapshot out in its own target format:
  - `pipenv` → a `Pipfile` (`toml.dump`), every group (`dev` included) flattened into `[packages]` — see the feature-family groups section above for why.
  - `uv` → native PEP 621 `[project]`/`[dependency-groups]` tables in `pyproject.toml`, plus `[tool.uv].default-groups` listing every group so they install without needing `--group`.
  - `poetry` → `[tool.poetry.*]` tables in `pyproject.toml`, one `[tool.poetry.group.<name>.dependencies]` per group, never marked `optional`.

  Each then calls `clear_dependency_sources(target_dir)` (removes `Pipfile`/`Pipfile.lock`, strips whichever dependency tables were previously there — from `pyproject.toml` or `Pipfile` — while preserving project metadata and `[build-system]`) and `set_package_manager_config(target_dir, "pipenv" | "uv" | "poetry")`.
- **Each format owns `[build-system]`/its own non-dependency `[tool.*]` table unconditionally, not via `setdefault`.** `poetry`'s `pre_install` always overwrites `[build-system]` with `poetry-core` and pops any leftover `[tool.uv]`; `uv`'s always sets `[tool.uv]\npackage = false` (uv's equivalent of Poetry's `package-mode = false` — without it, `uv sync` tries to build/install the generated project itself as a distribution and fails outright, since its top-level layout, `domain/`/`application`/`infrastructure/`/..., isn't a single installable package) and drops `[build-system]` entirely (irrelevant once `package = false`) and any leftover `[tool.poetry]`. This matters because `base`'s own `pyproject.toml` already ships a `[build-system]` key (plain `setuptools`, since `base` itself is package-manager-agnostic) — a `setdefault`-style "fill in only if missing" would silently never fire and leave the wrong backend in place after `poetry`'s own `pre_install` runs on a fresh `init` (caught and fixed 2026-10-08 while converting `base`'s manifest to pure PEP 621, see above).
- This runs in the **pre-install** phase — before `PackageManagerBase()` installs requirements — specifically so that class picks the *newly*-configured manager, not the old one (see the install-order note in [architecture.md](architecture.md)).
- **`appcraft.utils.dependency_convert` import must stay local to `pre_install`, not at module level.** This `__init__.py` is copied into every generated project as the `is_installed()` marker (`infrastructure/framework/appcraft/templates/<name>/__init__.py` — see [architecture.md](architecture.md)'s `project_init` bullet), but `appcraft.utils.dependency_convert` lives in the CLI package, which only exists in the dev environment — never inside a generated project. A module-level import would crash every generated project's marker file on any `is_installed()` check. All three templates declare `appcraft` as a **dev** dependency (in their own `pyproject.toml` fragment merged in by `TemplateAdder`) purely so pyright can resolve the import when editing appcraft's own source, with `# pyright: ignore[reportMissingImports]` since it still won't resolve inside an actual generated project that hasn't installed `appcraft` itself.

## Swap mechanics (`exclusive_group` + `uninstall()`)

`TemplateABC.install()` checks `cls.exclusive_group`: if set, it looks up every currently-installed template (via `TemplateManager`) sharing that same group and calls each one's `.uninstall()` before proceeding — generic engine behavior, documented in [architecture.md](architecture.md), not package-manager-specific code. `TemplateABC.uninstall()` (previously a no-op) now deletes whichever files `TemplateManager` recorded as that template's own (skipping any also owned by another still-installed template) and removes its `templates.json` entry — so `is_installed()` correctly flips after a swap, and per-template leftover files (like `poetry`'s `.vscode/settings.json`) don't linger. It does **not** duplicate the `Pipfile`/dependency-table cleanup — that's already handled unconditionally by the *newly*-installing manager's own `pre_install` → `clear_dependency_sources()` call above, regardless of which manager was active before.

Verified end-to-end (2026-09-21): `init` (poetry) → `add_template pipenv` → `add_template uv` → `add_template poetry` round-trips the same dependencies/metadata at every step, correctly removes/restores `.vscode/settings.json`, and `add_template pipenv uv` (two members of the group at once) raises `TemplateConflictError` as expected. Re-verified 2026-10-08 after the pure-PEP-621 conversion above (`init` with several templates installed at once → `add_template uv` → `add_template poetry`), including a real `uv sync`/`poetry install` on each side.

`TemplateAdder.union_dicts`' list-merge used to dedup with `set(dict1[prop])`, which silently assumed every merged list held hashable items — true as long as every list value was a plain string (Poetry's `authors = ["Name <email>"]`, or a dependency string). PEP 621's `authors` field is a list of *tables* (`[{name = ..., email = ...}]`), so merging `base`'s own fragment onto its freshly-copied self during `init` crashed (`unhashable type`) the moment `base/files/pyproject.toml` switched to this form. Fixed 2026-10-08 by switching the list merge to an equality-based membership check (`v not in dict1[prop]`) instead of a `set` — correct for any list element type, dicts included, at the cost of O(n·m) instead of O(n+m), irrelevant at the size these lists reach.
